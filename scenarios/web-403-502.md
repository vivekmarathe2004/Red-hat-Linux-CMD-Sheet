# Scenario: Web 403 Or 502

## What This Usually Means

This symptom tells you one layer of the system is not matching the expected state. Do not guess from the error message alone.

Collect evidence from service state, logs, ports, firewall, SELinux, DNS, storage, and package state until the failing layer is clear.

## Symptoms

- HTTP 403 Forbidden.
- HTTP 502 Bad Gateway.
- Web service starts but app is not reachable.

## Likely Causes

403:

- File permissions.
- SELinux labels.
- Directory index missing.
- Web server access rules.

502:

- Backend service down.
- Wrong proxy target.
- Backend listens only on another address.
- SELinux blocks proxy network connection.

## Decision Flow

Start broad, then narrow down. If the service is not running, read service logs. If it is running but unreachable, check listen address and firewall. If permissions look correct but access fails, check SELinux. If names fail but IPs work, check DNS.

## Diagnostic Flow

```bash
systemctl status httpd nginx
sudo apachectl configtest 2>/dev/null
sudo nginx -t 2>/dev/null
sudo ss -tulpn
sudo firewall-cmd --list-all
ls -lZ <docroot>
namei -l <docroot>
sudo ausearch -m AVC -ts recent
curl -I http://localhost
```

## Fix Options

For 403:

```bash
sudo chown -R <user>:<group> <docroot>
sudo chmod -R u=rwX,g=rX,o=rX <docroot>
sudo restorecon -Rv <docroot>
```

For reverse proxy 502 with SELinux:

```bash
sudo setsebool -P httpd_can_network_connect on
sudo systemctl restart httpd nginx
```

## Verification

```bash
curl -I http://localhost
sudo tail -f /var/log/httpd/error_log
sudo tail -f /var/log/nginx/error.log
```

## What To Remember

A good troubleshooting answer is not just a fix. It explains the evidence that led to the fix and the command used to verify recovery.

## Interview Answer

"For 403 I check permissions and SELinux labels. For 502 I check backend health, proxy target, listening ports, firewall, and SELinux proxy access."
